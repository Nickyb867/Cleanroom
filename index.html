An escrow deposit is only as good as what's inside it.

Escrow agreements protect you on paper. But a deposit that's incomplete, out of date or undocumented can't be turned back into working software, and you only discover that at the worst possible moment. These are the problems a proper verification catches.

Missing dependencies

Third-party libraries, internal packages or licensed components that exist on the developer's machine but were never deposited.

Undocumented build steps

Knowledge that lives in one engineer's head: environment variables, manual scripts, the order things have to be done in.

Source that doesn't match production

Code from an older release, or a branch that was never shipped, deposited in place of the version you're licensed to use.

Absent databases and configuration

Schemas, reference data, deployment settings and infrastructure definitions needed to actually run the application.

Tools nobody can obtain

Compilers, SDKs or build servers that are no longer available, or require licences the deposit doesn't account for.

Encrypted or unreadable files

Corrupt archives, password-protected content and files that can't be opened by anyone other than the vendor.

How a verification works.

We work directly with your software supplier's developers, so there's very little for your own team to do beyond agreeing the scope.

  1. Scope

    We agree the application, the release and the level of verification with you.

  2. Engage the vendor

    We talk to the supplier's developers to understand their build and deployment process.

  3. Rebuild in a clean room

    Starting from a blank machine, we rebuild the software using only what's in the deposit.

  4. Report

    You get a plain-English report with a clear result and a list of remediation actions.

  5. Re-verify

    When the supplier fixes gaps or ships a major release, we verify the updated deposit.

Common questions.

Do I need to change my escrow agent?

No. We verify deposits held with any escrow provider, or held directly under your own agreement with the supplier.

Does the software supplier need to be involved?

Yes, and that's a good thing. We talk to their developers to understand how the software is built, and any gaps we find go back to them to fix. Most suppliers welcome a verified deposit because it helps them win and keep customers.

How long does a verification take?

It depends on the size and complexity of the application. A deposit inspection is usually quick; a full verification of a large system takes longer. You'll get a timeline with your quote after the scoping call.

Where does the work happen?

In a secure, isolated environment with no access to the internet or the supplier's systems, either remotely or on site with the supplier if their security policy requires it.

What happens to the source code afterwards?

Build environments are securely wiped when the engagement ends. Source code is never retained, shared or reused.
